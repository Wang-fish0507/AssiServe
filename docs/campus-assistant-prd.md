# 校园助手小程序产品方案（V1）

## 1. 项目定位

**项目名（建议）**：CampusMate（校园搭子）  
**一句话定位**：一个面向本校学生的「可信问答 + 任务代办 + 校园生活服务」智能助手。  
**核心目标**：证明你不仅会调用模型 API，而且能完成从需求拆解、数据建设、RAG、Agent 编排到实际业务闭环。

---

## 2. 为什么这个项目有竞争力

和“通用法律条文助手”相比，这个项目的优势在于：

1. **强场景化**：围绕本校饮食、宿舍、教学楼、快递驿站、校历、选课、社团等高频问题。
2. **可验证真实性**：回答附带来源（校官网通知、后勤公告、地图点位、超市营业时间）。
3. **有动作能力**：不仅回答，还可执行动作（提醒、路线规划、订阅通知）。
4. **可扩展成 Agent 系统**：后续可增加课程表助手、考试周助手、迎新助手。

---

## 3. 目标用户与核心痛点

### 3.1 用户画像

- 大一新生：不熟悉校园地理和办事流程
- 在校生：高频查询生活服务信息
- 班委/社团成员：需要通知汇总与提醒

### 3.2 核心痛点

- 食堂/超市/驿站营业时间经常变动，信息分散。
- 宿舍报修、教学楼教室位置、办事地点难找。
- 通知更新快，错过重要时间节点（选课、缴费、考试安排）。
- AI 回答“看起来对”但不可信，缺少来源与时效判断。

---

## 4. MVP 功能设计（建议先做这 6 块）

### 功能 A：校园问答（RAG）

- 输入自然语言问题（如“菜鸟驿站今晚几点关门？”）
- 系统进行检索增强回答
- 输出带来源卡片（文档标题、发布时间、链接）
- 若无可靠来源，明确说“暂未查到，建议联系XX部门”

### 功能 B：校园地图与地点信息

- 支持查询食堂、超市、宿舍楼、教学楼、图书馆、快递点
- 展示位置、开放时间、联系方式、拥挤时段（可后续）
- 支持“从我当前位置到XX怎么走”（先接静态路线，再接地图 SDK）

### 功能 C：快递助手（菜鸟驿站场景）

- 查询驿站营业时间/高峰时段
- 快递取件提醒（用户自行记录取件码+提醒时间）
- 假期开放安排问答（来自公告 RAG）

### 功能 D：饮食助手

- 食堂窗口信息、开放时段、价格区间
- “现在还能吃什么”推荐（规则 + 简单偏好）
- 过敏原/忌口标签（后续）

### 功能 E：通知订阅与提醒

- 订阅类型：教务通知、后勤通知、奖助学金、校园活动
- 定时提醒：如“明天 8:00 提醒我去教三A楼 302 考试”
- 这部分可体现 Agent 的任务调度能力

### 功能 F：个人行程与任务助理（Agent）

- 解析用户意图：查询、提醒、路线、订阅
- 拆分子任务并调用工具（RAG 检索、地图、日程、消息推送）
- 返回“执行结果 + 下一步建议”

## 5. 技术架构（RAG + Agent + MCP）

## 5.1 总体架构

1. **小程序前端**：微信小程序（页面 + 组件 + 会话 UI）
2. **业务后端**：FastAPI / Node.js（鉴权、会话、任务、日志）
3. **RAG 服务**：文档处理、向量检索、重排、答案生成
4. **Agent 编排层**：意图识别 + 工具调用 + 记忆
5. **MCP 工具层**：标准化外部工具接入（地图、日程、公告源、数据库）
6. **数据层**：
   - 文档库（公告、指南、校历）
   - POI 库（楼宇、食堂、超市、驿站）
   - 用户数据（提醒、偏好、订阅）

## 5.2 RAG 设计细节

- **数据源**：学校官网通知、学院通知、后勤公告、迎新手册、办事流程文档
- **切分策略**：按“标题-段落-时间”分块，保留来源元数据
- **检索策略**：向量检索 + BM25 混合检索 + rerank
- **可信回答策略**：
  - 强制引用来源（至少1条）
  - 设置过期时间（如公告超过 6 个月降低权重）
  - 无证据则拒答/降级

## 5.3 Agent 设计细节

**建议做成 4 类工具 Agent**：

1. `CampusQAAgent`：负责问答和来源校验
2. `NavigatorAgent`：负责地点查询与路线规划
3. `ReminderAgent`：负责提醒创建、修改、取消
4. `SubscriptionAgent`：负责通知订阅与推送规则

**典型流程示例**：
- 用户：“明天早上提醒我去二食堂吃早饭，顺便告诉我最近的菜鸟驿站什么时候开门。”
- Agent 过程：
  1) 识别为“提醒 + 两个查询”复合意图
  2) 调用提醒工具创建日程
  3) 调用 POI 工具查询二食堂与驿站信息
  4) 调用 RAG 确认近期公告是否有临时调整
  5) 汇总回复并附来源

## 5.4 MCP 落地建议

你可以把 MCP 理解为“统一工具接口协议”，让 Agent 更规范地调用外部能力。  
建议至少接 3 个 MCP Server：

1. **Campus-POI MCP**：查询楼宇、食堂、超市、驿站基础信息
2. **Campus-Notice MCP**：访问通知文档索引与检索接口
3. **Campus-Schedule MCP**：创建/更新提醒任务

这样你在面试时能说清楚：
- 不是把所有逻辑写死在 Prompt 里
- 而是通过标准协议将“模型能力”和“业务工具”解耦

## 6. 数据库与数据表（最小可行）

- `poi`：地点信息（名称、类型、坐标、营业时间）
- `notice_docs`：通知文档（标题、正文、来源 URL、发布时间、向量ID）
- `user_profile`：用户偏好（口味、常用地点）
- `reminders`：提醒任务（时间、内容、状态）
- `subscriptions`：订阅配置（类型、推送频率）
- `chat_logs`：对话记录（问题、答案、引用来源、耗时）

---

## 7. 面试可讲的亮点指标（务必准备）

1. **准确性**：Top-K 检索命中率、人工评审正确率
2. **可信性**：带来源回答占比、拒答准确率
3. **性能**：P95 响应时延、工具调用成功率
4. **实用性**：7日留存、提醒任务完成率、订阅打开率

## 8. 实施路线图（8 周）

### 第 1-2 周：需求收敛 + 数据底座
- 确定 30 个高频问题
- 采集首批校园数据（POI + 通知）
- 搭建文档清洗与入库流程

### 第 3-4 周：RAG MVP
- 向量库 + 混合检索 + 引用回答
- 完成“无依据拒答”机制
- 做基础评测集（50~100问）

### 第 5-6 周：Agent + MCP
- 接入 3 个核心 MCP Server
- 实现复合任务编排（查询 + 提醒 + 订阅）
- 增加日志与可观测性

### 第 7-8 周：小程序体验打磨
- 对话页、地点页、提醒页
- 错误兜底与用户反馈入口
- 准备演示脚本和项目复盘文档
